# 정담 앱 제품 기획 하네스

이 문서는 정담 앱을 단순 기능 추가 앱이 아니라, 결혼식/장례식/경조사 전반을 관리하는 제품으로 기획하기 위한 하네스다.

## 목적

- 앱 전체를 먼저 파악한 뒤 필요한 기능을 제안한다.
- 결혼식과 장례식에 반드시 필요한 기능과, 사용자를 붙잡는 킥 기능을 구분한다.
- 기획, 디자인, 개발, 운영, 수익화 관점이 충돌할 때 토론 후 결론을 낸다.
- 모든 디자인 방향은 토스처럼 조용하고 명확하며 신뢰감 있게 간다.
- 경조사는 사용 빈도가 낮기 때문에, 평소에도 앱을 열 이유를 만드는 리텐션 기능을 반드시 검토한다.

## 제품팀 역할

제품 기획 작업을 할 때는 아래 역할들이 회의한다고 가정하고 각각의 관점을 낸다.

### Product Lead

- 정담 앱의 핵심 포지션과 우선순위를 정한다.
- 지금 당장 만들어야 할 기능과 나중에 해도 되는 기능을 나눈다.
- 기능이 많아져도 제품이 산만해지지 않게 정리한다.

### Wedding PM

- 청첩장, RSVP, 하객 관리, 축의금, 식대, 웨딩홀 견적, 감사 메시지 흐름을 본다.
- 결혼 준비자가 실제로 불편해하는 지점을 기능으로 바꾼다.

### Funeral PM

- 부고장, 조문객 관리, 조의금, 장례식장 안내, 감사 인사, 가족 공유 흐름을 본다.
- 장례 상황의 민감함, 속도, 신뢰, 단순함을 최우선으로 본다.

### Guest Experience PM

- 하객/조문객이 앱 설치 없이도 편하게 쓸 수 있는지 본다.
- 링크, QR, 지도, 계좌, 방명록, 답례 메시지의 마찰을 줄인다.

### Retention/Growth PM

- 경조사가 자주 발생하지 않는 문제를 해결한다.
- 사용자가 평소에도 앱을 열 이유를 만든다.
- 챙길 경조사, 관계 기록, 알림, 선물/답례, 일정, 감사 메시지, 지출 기록을 리텐션 관점에서 본다.

### UX Researcher

- 사용자의 불안, 귀찮음, 실수 가능성, 돈과 예의가 얽힌 민감함을 분석한다.
- 기능이 좋아 보여도 실제 사용자가 이해하기 어려우면 반대한다.

### Toss-style Product Designer

- 모든 화면을 토스처럼 명확하고 신뢰감 있게 설계한다.
- 기본 드랍다운, 기본 피커, 조악한 카드 나열을 피한다.
- 커스텀 바텀시트, 칩, 세그먼트, 명확한 CTA, 안정적인 여백을 우선한다.

### Tech Lead

- 구현 난이도, 데이터 모델, 결제/크레딧 위험, 배포 위험을 본다.
- 위험한 기능은 MVP와 나중 버전으로 쪼갠다.

### Revenue/Ops Lead

- 크레딧, 알림톡, 템플릿, 하객접수, 프리미엄 기능의 수익성을 본다.
- 운영자가 관리해야 할 데이터, CS 위험, 환불/결제 문제를 본다.

## 기획 루프 순서

제품 기획 요청을 받으면 바로 기능 목록을 뽑지 않는다. 아래 순서로 진행한다.

1. 앱 파악
   - 현재 코드 구조, 주요 화면, 이미 있는 기능, 결제/크레딧 흐름, 웹 연동을 훑는다.
2. 사용자군 분리
   - 결혼 주최자
   - 장례 주최자/상주
   - 하객/조문객
   - 경조사를 챙기는 일반 사용자
   - 관리자/운영자
3. 핵심 문제 정리
   - 결혼식에서 꼭 필요한 문제
   - 장례식에서 꼭 필요한 문제
   - 평소 사용 빈도가 낮은 문제
   - 돈/예의/관계 때문에 실수하면 안 되는 문제
4. 제품팀 토론
   - 각 역할이 기능 후보를 낸다.
   - 반대 의견과 위험도를 같이 적는다.
   - 기술 난이도와 사용자 가치를 비교한다.
5. 우선순위화
   - Must: 없으면 제품 경쟁력이 약한 기능
   - Kick: 있으면 “이 앱 좋다”가 되는 기능
   - Retention: 평소에도 앱을 열 이유가 되는 기능
   - Revenue: 수익화와 연결되는 기능
   - Later: 지금은 좋은데 나중에 할 기능
6. 작업서 변환
   - 선정된 기능을 작은 개발 작업서로 나눈다.
   - 각 기능마다 완료 조건, 디자인 기준, 검증 기준을 적는다.

## 기능 판단 기준

기능 후보는 아래 기준으로 점수화한다.

- 사용자 가치: 실제 불편을 해결하는가
- 빈도: 얼마나 자주 쓰이는가
- 신뢰: 돈/관계/예의를 더 안전하게 만드는가
- 차별성: 경쟁 앱보다 기억에 남는가
- 리텐션: 경조사가 없을 때도 앱을 열 이유가 되는가
- 수익성: 크레딧, 템플릿, 알림톡, 프리미엄과 연결되는가
- 구현 난이도: 지금 코드 구조에서 안전하게 만들 수 있는가
- 리스크: 결제, 개인정보, 민감한 감정, CS 위험이 있는가

## 정담 앱에서 반드시 검토할 기능 영역

### 결혼식 필수

- 모바일 청첩장
- RSVP 참석 여부
- 식사 인원 관리
- 지도/교통/주차 안내
- 계좌 전달
- 방명록
- 갤러리
- 축의금/하객 접수
- 감사 메시지
- 웨딩홀 견적/식대/정산

### 장례식 필수

- 모바일 부고장
- 장례식장 지도/주차/빈소 안내
- 조의금 계좌
- 조문객 명단
- 조의금 접수
- 감사 인사
- 가족 공동 관리
- 발인/입관/장지 일정 안내

### 경조사 앱 리텐션

- 챙길 경조사 관계 기록
- 내가 참석한 경조사 히스토리
- 축의금/조의금 얼마 했는지 기록
- 관계별 추천 금액
- 다가오는 경조사 알림
- 감사 메시지 보관함
- 주소/계좌/연락처 안전 보관
- 선물/답례 추천
- 결혼/장례 외 돌잔치, 개업, 회갑 등 확장 가능성

### 킥 기능 후보

- 관계 기반 축의금/조의금 추천
- 웨딩홀 견적 진단
- 행사 후 자동 정산 리포트
- 감사 메시지 자동 생성과 발송 기록
- 참석자 RSVP와 식권/식대 자동 예측
- 내 경조사 관계 그래프
- 내가 챙긴 사람/나를 챙긴 사람 기록
- 지역별 예식비 비교

## 디자인 원칙

- 토스처럼 흰 배경, 명확한 정보 계층, 큰 핵심 숫자, 작은 보조 설명을 사용한다.
- 기능 설명을 장황하게 노출하지 말고 사용자의 다음 행동을 버튼/상태로 안내한다.
- 기본 드랍다운을 쓰지 않는다.
- 선택 UI는 커스텀 바텀시트, 칩, 세그먼트, 검색 리스트 중 선택한다.
- 돈과 관계가 얽힌 화면은 장식보다 신뢰감, 확인 가능성, 실수 방지가 우선이다.
- 장례 관련 화면은 과한 색, 애니메이션, 장식 사용을 피한다.
- 결혼 템플릿 화면은 감성 표현을 허용하되 실제 정보 전달을 해치지 않는다.

## 산출물 형식

제품 기획 결과는 아래 형식으로 남긴다.

```md
## 앱 파악 요약

## 사용자군

## 현재 강점

## 현재 빈틈

## 제품팀 토론

### Product Lead
### Wedding PM
### Funeral PM
### Guest Experience PM
### Retention/Growth PM
### UX Researcher
### Product Designer
### Tech Lead
### Revenue/Ops Lead

## 기능 후보

## 우선순위

## 1차 개발 작업서

## 보류할 기능

## 검증 방법
```

## 금지

- 앱 전체를 보지 않고 기능을 막 추천하지 않는다.
- 결혼식 기능만 보고 장례식 기능을 무시하지 않는다.
- 경조사 빈도가 낮다는 문제를 무시하지 않는다.
- 토스 스타일이라고 하면서 색만 연하게 바꾸는 식의 디자인을 하지 않는다.
- 기본 드랍다운, 기본 alert, 기본 picker를 그대로 두고 디자인했다고 하지 않는다.
