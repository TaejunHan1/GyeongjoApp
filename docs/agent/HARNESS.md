# 정담 앱 하네스

이 문서는 정담 앱에서 AI 에이전트가 안정적으로 작업하기 위한 작업 울타리다. 프롬프트보다 우선하는 목적은 같은 실수를 반복하지 않게 만드는 것이다.

## 하네스 목적

- 작업 범위, 금지 영역, 검증 기준을 먼저 고정한다.
- UI, 결제, 데이터, 배포 작업이 섞이지 않게 분리한다.
- 실수나 사용자 피드백을 규칙으로 남겨 다음 작업에 반영한다.
- 한 번에 큰 변경을 하기보다 작은 루프를 반복한다.
- 제품 기획 작업은 `docs/agent/PRODUCT_PLANNING_HARNESS.md`를 함께 읽고 진행한다.
- 개발과 QA가 포함된 작업은 `docs/agent/DEVELOPMENT_QA_HARNESS.md`를 함께 읽고 진행한다.

## 작업 전 반드시 확인

1. `git status --short`로 현재 변경 파일을 확인한다.
2. 사용자가 요청한 최신 요구사항을 한 문장으로 정리한다.
3. 관련 파일을 먼저 읽고 기존 패턴을 파악한다.
4. 고위험 영역인지 판단한다.
5. 수정 범위와 검증 방법을 정한다.
6. UI/UX 작업이면 기획 의도, 화면 상태, 사용자 흐름, 디자인 기준을 먼저 정리한다.

## 기록 규칙

모든 작업 루프는 기록을 남긴다. 기록은 단순 완료 메모가 아니라 다음 에이전트가 이어받을 수 있는 수준이어야 한다.

기록 대상:

- 사용자 요구사항 원문 요약
- 작업 목표와 제외 범위
- 읽은 파일과 판단 근거
- 수정한 파일과 이유
- 디자인/기획 결정
- 검증 명령과 결과
- 실패, 되돌림, 사용자 피드백
- 다음 루프에서 해야 할 일

기록 위치:

- 현재 상태와 다음 루프: `docs/agent/LOOP_STATE.md`
- 반복 방지 규칙: `docs/agent/HARNESS.md`
- 특정 작업 목표와 완료 조건: `docs/agent/WORKORDER.md`
- 기능별 기획/개발/QA 기록: `docs/agent/features/<date-feature-name>/`

작업 후에는 최소한 `LOOP_STATE.md`의 `완료한 작업`, `검증`, `남은 문제`, `다음 루프 제안`을 업데이트한다.

코드 수정이 있는 기능 작업은 `FEATURE_SPEC.md`, `IMPLEMENTATION_LOG.md`, `QA_REPORT.md` 중 필요한 문서를 남긴다.

## 고위험 영역

아래 영역은 요청이 명확하지 않으면 건드리지 않는다.

- 크레딧 차감/충전 로직
- RevenueCat 결제 처리
- Supabase Edge Function 및 RPC
- `alimtalk_transactions`, `users.alimtalk_balance`, 결제 중복 방지 로직
- 하객접수 서명패드와 이름 인식 로직
- 앱 배포 버전 코드, bundle id, package name
- 기존 사용자 데이터 구조

## UI 작업 규칙

- 모바일 앱은 Android 작은 화면, Galaxy, iPhone Safe Area를 먼저 고려한다.
- 바텀시트, 모달, 입력창은 키보드가 올라왔을 때 가려지지 않아야 한다.
- 단계형 입력은 뒤로가기, 닫기, 진행 상태가 명확해야 한다.
- 존재하지 않는 버튼 자리를 억지로 비워두지 않는다.
- 드랍다운, 셀렉트, 피커는 플랫폼 기본 UI를 그대로 쓰지 않는다. 정담 앱 톤에 맞춘 커스텀 드랍다운, 바텀시트 선택기, 칩 선택기, 세그먼트 컨트롤 중 하나로 디자인한다.
- 옵션이 3개 이하이면 세그먼트/칩을 우선 고려한다.
- 옵션이 많으면 검색 가능한 바텀시트 선택기나 커스텀 리스트 모달을 우선 고려한다.
- 선택된 값, 비활성 상태, 에러 상태, 긴 텍스트 상태를 함께 설계한다.
- 지도, 달력, 청첩장 템플릿처럼 시각 기준이 중요한 작업은 실제 화면 기준으로 확인한다.
- 글자는 부모 영역을 넘지 않아야 한다.
- UI를 크게 바꾸면 최소한 JSX 파싱 또는 앱 실행 검증을 한다.

## 기획/디자인 절차

UI나 기능을 새로 만들 때는 바로 코딩하지 않는다. 먼저 아래 순서로 짧게 정리한다.

1. 사용자 상황: 누가, 어떤 순간에, 왜 이 화면을 쓰는가.
2. 핵심 행동: 사용자가 반드시 완료해야 하는 1개의 행동은 무엇인가.
3. 정보 우선순위: 가장 먼저 보여줄 정보, 숨겨도 되는 정보, 보조 정보.
4. 상태 설계: 기본, 로딩, 빈 상태, 에러, 성공, 키보드 표시, 작은 화면.
5. 입력 방식: 버튼, 칩, 토글, 커스텀 드랍다운, 바텀시트, 텍스트 입력 중 무엇을 쓸지.
6. 완료 기준: 사용자가 성공했다고 느끼는 순간과 검증 방법.

디자인 기준:

- 정담 앱은 토스처럼 조용하고 명확한 구조를 기본으로 한다.
- 큰 장식보다 정보 계층, 여백, 터치 가능 영역, 상태 피드백을 우선한다.
- 사용자가 반복해서 쓰는 운영 화면은 화려한 카드보다 밀도 있고 안정적인 구성이 우선이다.
- 청첩장/부고장 템플릿은 감성 표현이 중요하므로 시각 레퍼런스와 실제 미리보기 확인을 우선한다.
- 버튼 텍스트와 화면 제목은 사용자의 다음 행동을 분명히 말해야 한다.

## 제품 기획 작업 규칙

앱 전체 기능 기획, 신규 기능 제안, 리텐션 전략, 결혼식/장례식 필수 기능 정리는 제품 기획 작업으로 본다.

제품 기획 작업에서는 반드시 `docs/agent/PRODUCT_PLANNING_HARNESS.md`를 읽고 아래를 수행한다.

- 앱 전체 구조와 현재 기능을 먼저 파악한다.
- 결혼식, 장례식, 하객/조문객, 일반 사용자, 운영자 관점을 분리한다.
- Product Lead, Wedding PM, Funeral PM, Guest Experience PM, Retention/Growth PM, UX Researcher, Product Designer, Tech Lead, Revenue/Ops Lead 관점으로 토론한다.
- Must, Kick, Retention, Revenue, Later로 우선순위를 나눈다.
- 선정된 기능은 바로 개발하지 말고 1차 개발 작업서로 변환한다.

## 개발·QA 작업 규칙

코드 수정, UI 구현, DB 수정, 결제 로직 수정, 배포 준비는 개발·QA 작업으로 본다.

개발·QA 작업에서는 반드시 `docs/agent/DEVELOPMENT_QA_HARNESS.md`를 읽고 아래를 수행한다.

- Feature Spec 또는 작업서가 있는지 확인한다.
- 수정 전 영향 범위를 정리한다.
- 구현한 파일과 이유를 Implementation Log에 기록한다.
- 자동 검증과 수동 QA 체크리스트를 QA Report에 기록한다.
- 테스트하지 못한 항목은 이유와 수동 확인 방법을 남긴다.

## 결제/크레딧 작업 규칙

- 앱 클라이언트에서 직접 크레딧을 올리지 않는다.
- 결제 완료 반영은 RevenueCat Webhook과 Supabase Edge Function을 기준으로 한다.
- 같은 거래 ID는 한 번만 반영되어야 한다.
- 결제/크레딧 관련 수정은 테스트 이벤트와 실제 운영 이벤트를 구분한다.
- 결제 화면이나 크레딧 차감 타이밍을 수정하면 중복 차감, 중복 적립, 새로고침 손실을 반드시 확인한다.

## 웹 작업 규칙

- 앱과 웹이 같은 템플릿/인트로/지도 UI를 공유하는 경우 디자인 기준을 맞춘다.
- 웹 전용 깨짐은 웹 repo에서 수정한다.
- 로컬 서버가 필요하면 실행 URL을 사용자에게 알려준다.

## 루프 진행 방식

각 루프는 아래 순서로 진행한다.

1. 목표 확인
2. 관련 코드 읽기
3. 작은 수정 1개 적용
4. 검증 실행
5. 결과 기록
6. 다음 루프 제안

## 완료 조건

- 사용자가 요청한 기능이나 수정이 실제 코드에 반영되었다.
- 검증 결과를 확인했다.
- 검증하지 못한 항목은 이유와 수동 확인 방법을 남겼다.
- `docs/agent/LOOP_STATE.md`에 현재 상태가 업데이트되었다.

## 재발 방지 규칙

새 실수가 나오면 여기에 추가한다.

- 단계형 UI에서 1단계에 뒤로가기 버튼이 없으면 빈 자리도 만들지 않는다.
- Android 입력 모달은 키보드가 올라왔을 때 입력창이 가려지지 않아야 한다.
- 청첩장/부고장 생성 플로우에서 화면 전환 중 중복 터치로 알럿이 중복 표시되면 안 된다.
- 크레딧은 실제 생성 완료 전 차감되면 안 되고, 실패/새로고침 시 손실 방지 전략이 있어야 한다.
- 신규 킥 기능을 기획할 때 이미 홈/내 행사 상세/챙길 경조사/통계에 있는 기능을 이름만 바꿔 재노출하지 않는다. 기존 기능 재배치는 치명적인 기능으로 취급하지 않는다.
